  - v2（已批准 2026-11-08）：真实数据源接入，用爬虫 / 浏览器自动化 + 用户小红书账号替换样例数据

## 背景与目标

用户是个人小红书图文创作者。每天开始创作前最费时的一步是“今天写什么”，需要知道平台当前在流行什么；现在靠手动刷小红书，效率低、也不及时。

本产品（自媒体运营工作台）最终目标是覆盖“热点发现 → 图文生产 → 账号接入 → 一键发布”全链路。第一轮已交付「热点获取」模块（本地样例数据）。本轮把数据源换成真实小红书热点，让看板反映真实平台动态，为选题提供真实依据。

成功的样子：用户打开热点看板，能看到一份来自真实小红书的热点列表，每条含主题名、热度/排名、更新时间，且按设定频率自动更新。

判断指标（可观察）：
- 每次刷新后，热点列表非空，数据来自真实抓取（非本地样例），每条至少含主题名、热度/排名、更新时间。
- 自动刷新按设定频率发生（可通过“更新时间”的变化观察）。

## 目标用户与场景

- 目标用户：个人小红书图文创作者（当前即用户本人，单用户使用）。
- 场景：每天开始创作前，想快速知道“今天小红书在流行什么”，用来决定图文选题方向。

## 验收标准

| 用户故事 | 验收标准（当……时，应该……） |
| --- | --- |
| US-1 | 当打开热点看板时，应该显示一份非空的热点主题列表，每条至少包含主题名、热度或排名、更新时间。 |
| US-1 | 当热点数据暂时获取不到时，应该显示明确的空状态或错误提示，而不是空白页面。 |
| US-2 | 当到达设定的自动刷新时间点时，应该自动更新列表，且列表的“更新时间”随之更新。 |
| US-3 | 当点击“手动刷新”时，应该在短时间内返回最新列表并更新“更新时间”。 |
| US-4 | 当选择某个领域/主题筛选条件时，应该只显示该领域下的热点主题。（本轮不启用） |
| US-5 | 当打开热点看板时，应该显示来自真实小红书抓取的热点列表（数据来源为真实抓取，而非本地样例）。 |
| US-5 | 当真实数据源可用时，列表应反映小红书当前真实热点，且每条“更新时间”为本次真实抓取时间。 |
| US-6 | 当用户完成小红书登录授权后，系统应该能借助该登录会话抓取热点；会话失效时应提示用户重新登录，而不是静默失败。 |
| US-6 | 当尚未登录或会话失效时，应该显示明确的“需要登录”提示，而不是用样例数据冒充真实数据。 |

## 非目标

- 图文内容生产（选题、文案、配图）
- 账号接入功能（把账号用于发布 / 管理；本轮“登录小红书”仅作为数据抓取的依赖，不等同于账号接入）
- 一键发布
- 小红书以外的平台
- 用户未提出的：热点趋势曲线、收藏/标记、通知提醒、数据导出、多用户与登录体系

## 合规声明（本轮）

经用户明确要求“暂不考虑信息合规问题，先跑通流程”，本轮采用爬虫 / 浏览器自动化 + 用户自有小红书账号获取真实数据。此声明用于界定本轮范围；对外使用或上线前，须另行做合规与账号安全评估。

## 未决问题

- 登录方式：扫码 vs 账密 vs 手动登录后浏览器复用会话？推荐：手动登录后复用浏览器本地会话（不接触账密明文）。
- 登录会话持久化：会话（cookie）是否落盘复用？失效后如何处理？推荐：复用本地浏览器会话，失效即提示重新登录。
- 账号安全：账密 / 会话是否存储？推荐：不存账密，仅复用浏览器本地会话。
- 抓取频率对账号的风险：高频抓取是否触发风控 / 封号？推荐：先低频（沿用默认每 1 小时）观察。
- 热点条目字段最小集：沿用 v1 结论——主题名 + 热度或排名 + 更新时间。
- 单用户、本人使用，无需多账号体系：沿用 v1 结论——是。
